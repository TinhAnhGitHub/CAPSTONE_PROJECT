# Knowledge Graph Tasks

## Purpose

The `kg_graph` package turns segment captions into a resolved, queryable video knowledge graph. It builds three graph layers:

1. Entity layer: canonical people, objects, places, and entity-to-entity relationships.
2. Event layer: one segment-level event node per captioned segment, linked to entities and other events.
3. Micro-event layer: fine-grained event captions promoted into nodes and linked across nearby segments.

The final output is a `KGGraphArtifact`. `arango_indexing` later writes that artifact into ArangoDB.

## Tasks In This Package

| Prefect task | Implementation | Input | Output |
|--------------|----------------|-------|--------|
| `kg_extraction_chunk_task` | `KGExtractionTask` | `list[SegmentCaptionArtifact]` | `KGExtractionArtifact` |
| `kg_entity_resolution_task` | `run_entity_resolution()` | `list[KGExtractionArtifact]` | `KGEntityResolutionResult` |
| `kg_finalization_task` | `KGPipelineTask` | `KGEntityResolutionResult` | `KGGraphArtifact` |

## Dask Parallelization

The extraction stage is Dask-parallelized by the flow with `kg_extraction_chunk_task.map(extraction_batches, wait_for=segment_caption_futures)`. Each Dask worker receives a batch of segment captions and performs LLM extraction for that batch. Inside each extraction task, segment-level LLM calls are also run concurrently with `asyncio.gather()` and bounded by `max_concurrent` from `tasks.yaml`.

Entity resolution and finalization are submitted as single downstream Dask tasks because they need the complete video-level graph. They still run on Dask workers, but they cannot be safely mapped by segment because they need global duplicate detection, global IDs, and cross-segment edge construction.

## Stage 1: Per-Segment KG Extraction

Code: `extract_kg.py` and `KGExtractionTask`.

Input artifacts are `SegmentCaptionArtifact` objects that contain `summary_caption`, `event_captions`, timing, frame boundaries, and video IDs. `caption_segment_from_artifact()` converts each artifact into a lightweight `CaptionSegment`.

For each segment, `build_user_prompt()` sends this information to the LLM:

1. Segment time range.
2. Segment summary caption.
3. Atomic event captions from segment captioning.

The structured LLM output schema is `VideoGraphExtraction`:

| Field | Meaning |
|-------|---------|
| `entities` | Extracted entities with local IDs, name, type, description, and optional visual description. |
| `relations` | Subject-relation-object triples using local entity IDs or event IDs. |

Micro-events are not inferred again here. They are created directly from `event_captions` as `MicroEventDoc` objects so that the graph preserves the atomic observations generated by segment captioning.

After extraction, `globalize_ids()` replaces local per-segment IDs such as `entity_01` and `event_00` with UUID-based IDs. It also rewrites relationship endpoints to point to the new IDs. This prevents collisions when all segment graphs are merged.

Output is persisted as `KGExtractionArtifact` with raw segment KGs, raw entity count, LLM token counts, cost, and source segment caption artifact IDs.

## Stage 2: Entity Resolution

Code: `entity_resolution.py` and `kg_entity_resolution_task`.

The purpose is to merge repeated mentions of the same real-world entity across segments. A person or object can appear in many segments with slightly different names, so raw IDs from extraction are not enough.

The algorithm runs as follows:

1. `load_and_flatten()` sorts KG segments by time and flattens all raw entities into one list.
2. Each flattened entity receives a temporary `local_id`, a `belong_index` segment index, and a text representation: `entity_name: desc`.
3. `build_hybrid_clusters()` embeds all entity text with dense mmBERT embeddings and sparse SPLADE vectors.
4. Dense cosine similarity and sparse cosine similarity are combined as `hybrid_dense_weight * dense_sim + hybrid_sparse_weight * sparse_sim`.
5. Agglomerative clustering groups candidate duplicates using `distance_threshold = 1.0 - similarity_threshold`.
6. Large clusters are split into chunks of `max_entities_per_cluster` before LLM verification.
7. `resolve_cluster()` asks the LLM to split a candidate cluster into true real-world entity groups, produce a merged description, and choose a canonical name.
8. Single-entity clusters skip the LLM and become canonical immediately.
9. If the LLM fails, the code assigns `UNRESOLVED_*` IDs and preserves original names/descriptions instead of dropping entities.
10. `build_canonical_entities()` creates `CanonicalEntity` records and embeds canonical descriptions with mmBERT.
11. `remap_relationships()` rewrites raw relationships from raw entity IDs to canonical global entity IDs and collapses duplicate triples by increasing `weight`.
12. `build_resolved_kg()` creates `SegmentView` records, each containing the canonical entities and relationships visible in that segment.

Output is a `KGEntityResolutionResult`, not a persisted artifact. It carries the resolved KG, extraction artifact IDs, segment caption artifact IDs, total raw entity count, and accumulated cost tracker into finalization.

## Stage 3: Event And Micro-Event Linking

Code: `event_linking.py` and `KGPipelineTask.execute()`.

The purpose is to add temporal and semantic structure above the entity graph.

### Event Nodes

`build_event_docs()` creates one `EventNode` per resolved segment. Each event node contains:

| Field | Meaning |
|-------|---------|
| `key` | Stable key like `event_0003`. |
| `caption` | Segment summary caption. |
| `entities_global` | Canonical entities present in the segment. |
| `micro_events` | Raw micro-event strings from event captions. |
| `embedding` | Dense mmBERT embedding of the event caption. |

`build_event_entity_links()` then connects each event to the canonical entities it contains.

### Event Edges

`build_event_edges()` uses a four-pass algorithm:

1. Pass 1 adds `NEXT_EVENT` edges between consecutive segment events to preserve temporal order.
2. Pass 2 adds `SEMANTICALLY_SIMILAR` edges when event-caption embedding cosine similarity is above `semantic_threshold`.
3. Pass 3 adds `SHARES_CONTEXT` edges when the Jaccard overlap of entity sets is above `jaccard_threshold`.
4. Pass 4 sends borderline similarity pairs above `llm_confirm_threshold` to the LLM. The LLM can confirm `SEMANTICALLY_SIMILAR`, `SHARES_CONTEXT`, `CAUSAL`, or reject as `UNRELATED`.

Each event edge stores temporal gap, similarity when available, number of shared entities, optional Jaccard score, and optional LLM reason.

### Micro-Event Nodes

`build_micro_event_nodes()` turns every event caption string into a `MicroEventNode`. Micro-events inherit their parent event key, segment timing, parent caption context, and parent canonical entity IDs. Their text is embedded with mmBERT.

### Micro-Event Edges

`build_micro_event_edges()` uses the same four-pass logic as event edges, but only compares micro-events within a sliding segment window (`micro_window_size`). This bounds the combinatorial cost while still linking related fine-grained events across nearby segments.

Micro-edge types are `SEMANTICALLY_SIMILAR_MICRO`, `SHARES_CONTEXT_MICRO`, and `CAUSAL_MICRO`, with LLM fallback for borderline pairs.

## Final Output

Type: `KGGraphArtifact`

| Field | Meaning |
|-------|---------|
| `entities` | Canonical entity documents. |
| `relationships` | Canonical entity-to-entity relationships. |
| `segment_views` | Per-segment resolved views for retrieval. |
| `events` | Segment-level event nodes. |
| `event_entity_links` | Event-to-entity edges. |
| `event_edges` | Event-to-event sequence/context/semantic/causal edges. |
| `micro_event_nodes` | Fine-grained event nodes. |
| `micro_event_edges` | Micro-event semantic/context/causal edges. |
| `total_*` fields | Graph statistics and LLM usage/cost. |

## Failure Behavior

Extraction failures for a segment return an empty `KGSegment` for that segment, preserving timing and captions. Entity-resolution LLM failures preserve entities as unresolved singleton groups. This favors incomplete graphs over pipeline failure.

## Downstream Consumer

`arango_indexing_task` consumes the `KGGraphArtifact` and writes graph vertices and edges into ArangoDB collections.
